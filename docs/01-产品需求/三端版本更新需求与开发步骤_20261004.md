# 倾境动态壁纸三端版本更新需求与开发步骤

版本：1.0；日期：2026-10-04。本文只记录本次新增功能，由用户明确授权编写，不维护历史 1.0 文档或项目看板。

## 一、概述

### 已确认的需求与范围

用户视角：现有 Android、iOS、HarmonyOS 用户需要在发现严重缺陷后停止使用有问题的旧版本，普通改版仍可选择继续使用。无需新增登录。

业务视角：长期维护现有壁纸 App，更新功能本身不收费，不改变首免、兑换、苹果支付和壁纸交付规则。已付款交易的验证和恢复不能因强制更新而丢失。

技术视角：Java API、MySQL、现有 FileStorage Adapter、独立管理后台、Flutter Android/iOS、ArkTS HarmonyOS。安卓从服务器直接下载正式 APK；苹果、鸿蒙跳转各自应用商店。

概念方案：管理后台分别管理三端版本；API 计算最低允许版本与最高可用版本；App 在启动、恢复前台及业务被拦截时显示普通或不可关闭更新提示。

包含：版本录入、APK 上传解析、发布、强制开关、弃用、版本检查、APK 下载及覆盖安装、应用商店跳转、服务端业务拦截。

不包含：生产部署、发布应用商店版本、静默安装、H5、自动上传应用商店、用户账号系统、旧版本降级安装、推送或持续轮询。

成功标准：三端策略互不影响；普通更新可关闭；强制更新无法通过返回、点遮罩、重启离线绕过；关闭强制或弃用后可恢复使用；安卓更新无需卸载、使用同包名同签名的递增版本覆盖安装。

参考：用户提供的《华音Android强制更新前后端开发说明_20261004.md》仅作参考，具体规则以本次确认内容为准。苹果更新流程：https://support.apple.com/en-ie/102629；鸿蒙更新说明：https://consumer.huawei.com/cn/support/content/zh-cn16064441/。

## 三、页面结构与导航

管理后台新增侧栏「App版本管理」，页签为 Android / iOS / HarmonyOS。上方展示本平台最低允许使用版本与最新可用版本，列表展示版本、更新说明、状态、是否强制、交付入口、时间和操作。

安卓新增版本入口：选择 APK → 上传并解析 → 展示真实包信息 → 保存为草稿 → 发布。

苹果/鸿蒙新增版本入口：填写版本和商店链接 → 保存为草稿 → 确认商店已可更新 → 发布。

App 不新增主导航页面。隐私同意后先检查更新；普通更新以可关闭弹窗覆盖业务，强制更新以根层门禁覆盖所有业务页面。强制提示只有「立即更新」「重新检查」，没有关闭、稍后、忽略。

更新界面展示当前版本、实际更新目标（安卓版本 / 商店最新版本）、更新说明、状态与错误。不向用户展示后台 build、签名、公钥或内部接口细节。

## 四、规则与状态

### 1. 版本线性规则

- 三个平台独立计算。版本不能按字符串字典序排序，例如 1.10 高于 1.9。
- 安卓、鸿蒙按真实整数 versionCode 排序；iOS 按数字营销版本 versionName 排序。同一营销版本的构建号变化不能造成商店用户无法完成的强制更新。
- 每个版本状态为 DRAFT（草稿）、PUBLISHED（已发布）、DEPRECATED（已弃用）。只有 PUBLISHED 参与判断，多个版本可同时生效。
- 最新可用版本：所有 PUBLISHED 中最高的版本。
- 最低允许使用版本：所有 PUBLISHED 且 forceUpdate=true 中最高的版本。用户低于该版本时强制更新；达到该版本时可以继续使用。
- 关闭某版本强制后，它变成普通更新，其他仍生效的强制版本继续参与判断。
- 弃用后保留记录，停止作为更新目标或强制门槛。不是删除用户 App，也不是降级。
- 更新只指向高于本机的可用版本，不会提示安装相同版本或更低版本。

| 生效版本 | 本机 | 结果 |
|---|---|---|
| 2 普通、3 强制、4 普通 | 1 / 2 | 不可关闭；安卓安装最新可用 APK 4，苹果/鸿蒙前往商店更新最新 |
| 同上 | 3 | 可关闭的 4 更新提示 |
| 同上 | 4 / 5 | 无更新提示 |
| 2 / 3 / 4 全弃用 | 1 | 无提示 |
| 2 / 3 / 4 弃用，5 普通 | 1 | 可关闭的 5 更新提示 |
| 3 关闭强制，2 普通、4 普通 | 1 | 可关闭的 4 更新提示 |

### 2. 后台操作

上传不生效；保存草稿不生效；点击发布后参与检查。强制默认关闭，不因上传新包自动拦截用户。发布苹果/鸿蒙版本时管理员必须确认商店已发布、用户确实能够更新；不能把审核中版本设为正式更新目标。

| 字段 | 规范 |
|---|---|
| platform | android / ios / harmony；创建后不可修改 |
| versionName | 必填，数字点分版本，最多 3 段；显示正式营销版本 |
| versionCode | 必填，正整数；安卓从 APK 解析，其他平台从正式构建填写 |
| releaseNotes | 最多 1000 字，可留空 |
| forceUpdate | 布尔，默认 false；可关闭，不保留独立残余最低版本限制 |
| storeUrl | 苹果/鸿蒙必填，官方应用商店 HTTPS 地址；安卓不使用 |
| APK | 正式包，自动解析包名、版本、ABI、证书摘要，计算 SHA-256 和大小，校验 APK 签名；限制上传大小，拒绝错误类型和无效签名 |
| status | 草稿 → 发布 → 弃用；弃用版本不重新加入当前规则 |

同平台不得存在重复版本。安卓新正式包必须与已发布正式包同包名同签名，版本递增；草稿尚未完成解析或商店字段不合法不能发布。

后台空状态：「暂无版本，请先添加正式版本」。加载：「正在获取版本」。成功：「版本已发布」「强制更新已关闭」「版本已弃用」。失败展示 API 提供的可读说明，保留用户已填内容。管理会话失效按既有登录流程处理。上传超时/网络断开允许重新上传；禁止连续点击造成重复发布。

### 3. App 门禁状态机

| 状态 | 进入条件 | 退出条件 / 表现 |
|---|---|---|
| checking | 隐私同意后启动、恢复前台、业务收到 APP_UPDATE_REQUIRED、手动重新检查 | 同一时刻仅一个请求，重复触发合并 |
| noUpdate | 无有效更高版本 / 当前已符合最新版本 | 进入业务 |
| optional | 有新版本且本机达到最低允许版本 | 可关闭；本次运行已忽略的同一目标不重复弹 |
| required | 本机低于最低允许版本 | 无法操作业务；遮罩、系统返回、路由切换不能关闭 |
| downloading | 安卓点击更新 | 显示进度，成功进入校验；失败可重试，强制门禁仍保留 |
| verifying | 安卓下载完毕 | 比对 SHA-256、大小、包名、版本和安装签名；失败删除错误包并重试 |
| installing / store | 调起系统安装 / 商店 | 返回后重新检查本机真实版本；仅点击按钮、取消安装不解除门禁 |
| error | 检查或更新失败 | 首次未确认强制时不全局锁死；已确认强制时显示重试且维持门禁 |

本机版本必须读取系统包元数据，不从写死常量、显示文本或 pubspec 基础值判断。初次检查在设备身份/session 初始化前，更新接口无需设备鉴权，避免旧版本身份被拒而无法获取更新入口。

首次检查网络失败允许进入业务，不把后端异常误认为强制更新。已确认的强制策略持久化到本地；重启或断网仍维持已知门禁。新版本或成功检查返回撤销策略时清除缓存。成功联网检查结果优先于缓存。普通提示不写成永久封禁记录。

普通弹窗：「发现新版本」「立即更新」「稍后」。苹果/鸿蒙强制说明：「当前版本已不再支持，请前往应用商店更新至最新版本。」安卓强制说明：「当前版本已不再支持，请更新后继续使用。」失败：「更新检查失败，请重试」「下载失败，请重试」「安装包校验失败，请重新下载」。恢复前台时重新检查，后台无持续轮询。

### 4. 安卓直接更新

后台最高可用 APK → 专用下载接口 → App 私有缓存 → 校验 → FileProvider → 系统安装确认 → 同包名同签名覆盖升级。用户需要授予此 App 安装未知应用权限时跳系统设置，返回后继续安装。取消或失败仍允许重试；强制弹窗保持拦截。

安装包不得写入公开共享下载路径；只向系统安装器授予临时只读访问。下载使用 HTTPS，拒绝跨域/降级跳转；校验实际包版本高于本机、目标一致、签名与本机一致。旧下载缓存不能串用为新目标。服务端支持 Range，客户端中断后可重试/续传。

### 5. 服务端门禁和支付保护

客户端在业务请求附带 X-App-Version-Name、X-App-Version-Code。服务端从已验证会话获取平台，独立重新计算规则，不能只依赖不可关闭的 UI。

受限业务：创建新的兑换、首次免费获取、新购买意图、下载票据。命中返回 HTTP 426 / APP_UPDATE_REQUIRED，App 重新检查并进入根门禁。已有付费交易的验签确认、恢复和通知回调继续工作，不能因更新策略吞掉已付款权益。更新检查、APK 下载、必要的身份初始化不被更新门禁阻止。

版本声明仅用于升级管理，不替代 App Attest、DeviceCheck 或业务验签，也不宣称它可阻止篡改客户端伪造版本。

## 五、API 契约与存储

| 接口 | 用途 |
|---|---|
| GET /api/v1/app-updates/check | 公开检查；platform、versionName、versionCode |
| GET /api/v1/app-updates/packages/{id} | 公开下载已发布安卓 APK，支持 Range、只允许记录对应文件 |
| GET /api/v1/admin/app-releases?platform=… | 管理版本列表 |
| POST /api/v1/admin/app-releases/android | multipart APK 上传解析，file / releaseNotes |
| POST /api/v1/admin/app-releases | 苹果/鸿蒙版本录入 |
| PUT /api/v1/admin/app-releases/{id} | 编辑说明、强制开关、商店链接 |
| POST /api/v1/admin/app-releases/{id}/publish | 发布草稿 |
| POST /api/v1/admin/app-releases/{id}/deprecate | 弃用 |

检查响应沿用既有 envelope，data 含 platform、updateAvailable、mandatory、minimumVersion、latestVersion、checkedAt。版本结构含 id、platform、versionName、versionCode、releaseNotes、forceUpdate、status、deliveryType、storeUrl、packageName、sha256、fileSize、abi、signerSha256、downloadUrl、createdAt、publishedAt；不存在的字段为 null。

MySQL 是版本和策略事实的唯一来源，通过 Flyway 新增版本表；关闭/弃用应立即使新检查反映新规则。安装包使用现有 FileStorage 接口，不向业务暴露物理路径。APK 只通过独立记录下载入口发布，绝不公开整个壁纸存储目录。安装包独立于服务器 API JAR / 管理后台前端的部署目录保存。

## 七、上线顺序与限制

先部署 API/管理后台，再发布包含本功能的三端 App。当前已经安装且不含本功能的旧包无法凭空出现更新弹窗，首次覆盖安装/商店发布后才具备客户端更新门禁；服务端可以控制对应旧版业务请求。

安卓先上传并校验正式新包，再发布更新记录；苹果/鸿蒙先确认商店新版本可下载，再发布更新规则。新正式构建必须同步现有设备身份/苹果验证的构建允许名单，不因升级使支付或设备注册失效。

发生误拦截时，关闭有效强制开关或弃用对应版本；App 成功重新检查后解除。修复版本使用递增版本重新发布，不向用户安装较低版本。生产操作遵循现行 OPS-005，另行授权后执行。
