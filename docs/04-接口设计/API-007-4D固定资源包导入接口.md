# API-007 4D 固定资源包导入接口

**日期：** 2026-09-15

**状态：** API、数据库及管理后台已实现并通过本地联调；OpenAPI 1.5.0。Android 短验收待连接设备，见 [WP-UI05 验收记录](../06-测试与验收/WP-UI05-4D固定ZIP后台与API验收-2026-09-15.md)。

**关联：** [管理后台改造说明](../01-产品需求/IXD-WP-ADMIN-002-4D固定资源包上传改造.md)、[API-002](API-002-管理身份与内容API实现说明.md)、[现有内部图层配置](../../packages/wallpaper-format/parallax-config-v2.schema.json)

## 1. 目标与职责

运营只上传一个 ZIP，服务端解析出封面、多层图片和配置，生成现有资源绑定。这样可以支持 2～12 层作品，避免逐项上传混入不同版本，也把校验统一放在服务端。

源 ZIP 仅用于管理导入。客户端继续读取既有公开封面、受控预览包和授权后的正式加密包。服务端不能把源 ZIP 或原始图层永久链接放进公开目录；未获得权益的预览继续通过现有降质、水印和加密流程生成。

本次新增管理导入接口和源包数据记录；公共/设备下载协议及 Android 渲染格式保持兼容。

## 2. 固定 ZIP 结构

```text
任意文件名.zip
├── cover.jpg
├── config.json
└── layers/
    ├── 01.png
    ├── 02.png
    └── 03.jpg
```

| 项目 | 固定要求 |
|---|---|
| 根目录 | 直接包含 `cover.jpg`、`config.json`、`layers/`，不能套作品名称文件夹 |
| 封面 | 文件名严格为 `cover.jpg`，实际内容 JPEG；用作列表缩略图，不是原图下载入口 |
| 图层文件名 | `layers/NN.ext`，NN 为 `01`～`12`；从 `01` 连续编号到 N，不得跳号、重号，同编号不能出现两个扩展名 |
| 图层数量 | N 为 2～12，必须与 JSON 数组项数一致 |
| 层级 | `01` 最近，N 最远；N 是唯一背景，其他全是前景；先绘制 N，最后绘制 01 |
| 前景格式 | `.png` 或 `.webp`，实际图片必须有透明通道 |
| 背景格式 | `.jpg`、`.png` 或 `.webp`，实际像素必须完全不透明、铺满画布 |
| 尺寸 | 每个图层宽高严格等于 `canvas`；宽、高均为整数 512～4096，禁止依赖 EXIF 旋转才能对齐 |
| 封面尺寸 | 宽、高各 1～4096，建议 1080×2160；不必与图层等大，建议相同比例 |
| 动画图片 | 不接受动画 WebP/APNG；图层必须是单帧图片 |
| 大小 | ZIP ≤100 MiB；cover ≤20 MiB；源 config ≤64 KiB；每张图层 ≤50 MiB；图层加生成的内部 config 合计 ≤64 MiB，复用现有安全包上限 |
| 解压预算 | 所有条目实际展开合计 ≤85 MiB，最多 64 条目，包含目录与忽略项；读取过程中计数，不能只信 ZIP 声明 |

字母、目录和扩展名使用小写。允许空的 `layers/` 目录条目。为兼容系统压缩工具，可忽略 `__MACOSX/` 下的普通元数据文件和任意目录中的 `.DS_Store`，但仍计入解压预算；它们不能参与编号、配置或资源绑定。其余额外文件一律报错，不静默猜测文件用途。

解压前和过程中拒绝绝对路径、`..`、反斜杠、符号链接、重复路径/大小写冲突、加密 ZIP、嵌套压缩包及不支持的压缩算法。仅允许 STORE/DEFLATE，检查 CRC 和实际媒体内容。流式写入隔离暂存区，业务层通过存储 Port 操作，不拼接用户路径到正式资源目录。

## 3. 源 config.json

UTF-8 JSON，无 BOM，无重复键、尾随内容和未知字段。根字段必须完整存在；不接受 URL、资产 ID、任意文件路径或脚本。下面是可直接使用的三层配置：

```json
{
  "formatVersion": 1,
  "canvas": { "width": 1080, "height": 2160 },
  "sensor": { "maxAngle": 10, "smoothing": 0.2, "strength": 1 },
  "layers": [
    { "index": 1, "depth": 1, "scale": 1.1, "opacity": 1, "blendMode": "normal" },
    { "index": 2, "depth": 0.5, "scale": 1.05, "opacity": 1, "blendMode": "normal" },
    { "index": 3, "depth": 0, "scale": 1, "opacity": 1, "blendMode": "normal" }
  ]
}
```

| 字段 | 规则 |
|---|---|
| `formatVersion` | 整数，固定为 1，表示运营源包格式版本，与 App 正式包 formatVersion 无关 |
| `canvas.width/height` | 与所有图层一致，见尺寸规则 |
| `sensor.maxAngle` | 数值 5～25，单位度 |
| `sensor.smoothing` | 数值 0.05～0.5，姿态平滑参数 |
| `sensor.strength` | 数值 0～2；0 表示静止，各层仍按遮挡顺序合成 |
| `layers` | 数组按 index 1→N 排列，各项严格包含示例中的五个字段，不能缺项或重复 |
| `index` | 整数，等于对应两位文件名编号 |
| `depth` | 数值 0～1，从 01 到 N 非递增；越大位移越强；背景固定为 0 |
| `scale` | 数值 1～1.5，为预留边缘的放大比例 |
| `opacity` | 数值 0～1；背景固定 1 |
| `blendMode` | `normal`、`screen`、`add`；背景固定 `normal` |

所有数值必须有限，不做静默裁剪或默认补全。封面由设计人员提供合成结果，服务端不凭封面反推图层，也不承诺自动判断封面与合成画面语义相同。

## 4. 转换成现有 App 格式

运营文件按前到后编号，App 内部配置按后到前绘制。服务端转换如下，不能直接把源 config 塞进客户端安全包：

| 源图层 | 内部 role | 内部 ordinal | 内部配置位置 |
|---|---|---|---|
| N（背景） | `BACKGROUND` | 0 | 第一个 |
| N−1 … 02 | `FOREGROUND` | index−1 | 依编号逆序排列 |
| 01（最前景） | `FOREGROUND` | 0 | 最后一个 |

例如三层转换后顺序是 `BACKGROUND:0`、`FOREGROUND:1`、`FOREGROUND:0`。ordinal 在每个 role 内唯一，不要求跨 role 唯一。即使 depth 相同，也保持编号逆序，保证遮挡关系。

生成的内部 JSON 去掉 `formatVersion`，保留 `canvas`、`sensor`，每项 `index` 替换为 `role`、`ordinal`，严格满足既有 `parallax-config-v2.schema.json` 和 `SecurePackagePublisher` 校验。资源绑定包括 N 张图层及一个 `PARALLAX_CONFIG:0`；cover 保存为 `WALLPAPER_COVER` 用于壁纸元数据，不混入 4D 渲染图层。

## 5. 导入并解析 ZIP

```http
POST /api/v1/admin/parallax-packages
Content-Type: multipart/form-data
Cookie: {现有管理员会话}
X-CSRF-Token: {csrfToken}
X-Request-Id: {uuid}

file=@wallpaper-4d.zip
```

只需要 `file` 字段，不经过通用 `/admin/assets`，不要求前端解压或额外发送 role、coverAssetId。管理员身份、CSRF、限流和审计沿用现有管理 API。

同步解析成功返回 `201`，已经存在同一 SHA-256 且仍有效的包可返回 `200` 并复用 ID。只有全部校验通过、资源存储与数据库登记成功后，才返回 `READY`。当前前端不支持 `202` 或 `VALIDATING` 轮询。

```json
{
  "id": "90",
  "originalFilename": "wallpaper-4d.zip",
  "mimeType": "application/zip",
  "sizeBytes": 23891234,
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "validationStatus": "READY",
  "cover": {
    "id": "901",
    "originalFilename": "cover.jpg",
    "mimeType": "image/jpeg",
    "sizeBytes": 180000,
    "validationStatus": "READY",
    "previewUrl": "/api/v1/admin/assets/901/content"
  },
  "canvas": { "width": 1080, "height": 2160 },
  "layers": [
    { "index": 1, "originalFilename": "layers/01.png", "role": "FOREGROUND", "ordinal": 0, "depth": 1, "scale": 1.1, "opacity": 1, "blendMode": "normal" },
    { "index": 2, "originalFilename": "layers/02.png", "role": "FOREGROUND", "ordinal": 1, "depth": 0.5, "scale": 1.05, "opacity": 1, "blendMode": "normal" },
    { "index": 3, "originalFilename": "layers/03.jpg", "role": "BACKGROUND", "ordinal": 0, "depth": 0, "scale": 1, "opacity": 1, "blendMode": "normal" }
  ]
}
```

全部 ID 均为字符串。响应 layers 按源 index 升序，内部绘制配置才反转。`sha256` 由服务端计算，示例为占位。`previewUrl` 是现有带管理员鉴权的资源地址；不返回源 ZIP 地址和内部存储路径。

导入阶段只制作媒体资产和内部配置，不需要 wallpaperId，不生成最终签名包。最终签名包需要资源版本身份，在后面的现有 secure-package 步骤生成。

## 6. 用源包创建资源版本

```http
POST /api/v1/admin/variants/{variantId}/parallax-resource-versions
Content-Type: application/json
X-CSRF-Token: {csrfToken}
X-Request-Id: {uuid}

{
  "versionNo": 2,
  "sourcePackageId": "90"
}
```

成功返回 `201 AdminResourceVersion`。字段沿用现有版本模型，并新增完整的 `sourcePackage`（第 5 节模型）；`bindings` 仍返回实际生成的图层和配置绑定。版本状态为 `READY`，还未发布。

服务端校验 variant 属于可编辑壁纸且为 Android `LAYER_PARALLAX`、源包存在且有效、versionNo 合法、每个资产为 READY。事务内写版本、绑定、源包关联及审计，不能留下少层版本。

同一个 variantId＋versionNo＋sourcePackageId 重试返回原版本 `200`；相同 variantId＋versionNo 绑定不同包返回 `409 STATE_CONFLICT`。对编号竞争通过数据库唯一约束保证一致性。`X-Request-Id` 用于追踪，不当作幂等键；源包 SHA 去重和上述三元组负责重试语义。

## 7. 扩展现有响应与调用顺序

所有管理接口返回 `AdminResourceVersion` 时增加 `sourcePackage`。包括壁纸列表所读取的详情、版本创建、发布和安全包制作响应。新源包版本返回完整描述；历史逐项上传版本返回 `null`。变体内 `resourceVersions` 按 versionNo 降序返回，前端优先选最新 READY，再选 PUBLISHED。

管理后台已按以下顺序调用：

1. 新选 ZIP：`POST /admin/parallax-packages`。
2. 取返回 `cover.id`，用现有 `POST/PATCH /admin/wallpapers` 保存基础信息；PATCH 沿用 `If-Match`。
3. 新建作品如尚无变体，调用既有 `/admin/wallpapers/{id}/variants` 创建 Android `LAYER_PARALLAX`。
4. 包变化时调用本次 `parallax-resource-versions`，versionNo 为现有最大值加 1。
5. 发布时调用既有 `/admin/resource-versions/{id}/secure-package` 制作正式包和预览包，再调用 `/admin/wallpapers/{id}/publish`。
6. 保存草稿则重读壁纸详情。新包和当前可用版本关联一致时复用版本，不重复导入或增版。

以上是多步流程，整体不承诺一个事务。后续失败时基础信息（包括新 cover）可能已保存；旧已发布资源版本仍有效，前端保留作品 ID 和已完成进度以便重试。服务端不能因包制作失败把整件旧作品删除或将半成品作为当前正式版本。

## 8. 错误响应

继续使用现有 `ErrorEnvelope`。结构、图片、JSON 的具体错误统一返回 `PARALLAX_PACKAGE_INVALID`，通过中文 message 和 details 指出原因，避免前端猜测。

```json
{
  "error": {
    "code": "PARALLAX_PACKAGE_INVALID",
    "message": "layers/02.png 尺寸为 800×1600，与画布 1080×2160 不一致",
    "requestId": "00000000-0000-4000-8000-000000000001",
    "details": [{ "field": "layers/02.png", "reason": "DIMENSION_MISMATCH" }]
  }
}
```

| HTTP | code | 用途 |
|---|---|---|
| 400 | `PARALLAX_PACKAGE_REQUIRED` | 缺少 file/sourcePackageId |
| 413 | `PAYLOAD_TOO_LARGE` | ZIP、展开字节、单文件或现有安全包字节超限 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 非 ZIP 或不支持的媒体类型 |
| 422 | `PARALLAX_PACKAGE_INVALID` | 目录、编号、JSON、尺寸、透明通道、文件损坏等不合规则 |
| 404 | `RESOURCE_NOT_FOUND` | 源包或变体不存在，源包已回收 |
| 409 | `STATE_CONFLICT` | 版本编号竞争、变体类型不匹配或不允许编辑 |
| 409 | `PARALLAX_PACKAGE_IN_USE` | 源包已被版本引用，清理时拒绝删除 |
| 412 | `VERSION_CONFLICT` | 既有壁纸元数据更新的乐观锁失败 |

details.reason 建议固定为 `STRUCTURE_INVALID`、`LAYER_SEQUENCE_INVALID`、`LAYER_COUNT_INVALID`、`CONFIG_INVALID`、`DIMENSION_MISMATCH`、`ALPHA_REQUIRED`、`BACKGROUND_NOT_OPAQUE`、`CORRUPT_FILE`；不把绝对路径和异常堆栈交给前端。

## 9. 数据、资源与兼容

通过新 Flyway 迁移增加源包及图层记录，建议结构为 `parallax_source_package`、`parallax_source_layer`，resource_version 增加可空的 source_package_id 外键。字段至少保存 SHA、文件名、大小、私有存储键、cover_asset_id、config_asset_id、画布、源格式版本、状态、创建者与时间；图层记录保存 index、asset_id、role、ordinal 及渲染参数。业务事实以 MySQL 为准，Redis 不保存唯一的源包解析结果。

复用已有资产用途 `WALLPAPER_COVER`、`BACKGROUND`、`FOREGROUND`、`PARALLAX_CONFIG` 和 FileStorage Port。源 ZIP 独立私有保存，不以通用可公开资产方式交付。发布器继续从不可变绑定构建预览和正式包。

解析失败需回滚数据库登记并清理本次暂存文件；文件清理失败记录待清理任务，不能返回 READY。相同 SHA 并发导入应复用一个有效包。可清理超过 24 小时且无任何业务引用的孤立包；清理前重新核验源包、图层、封面和版本引用，不能删除已经被壁纸元数据或版本使用的资产。

旧版 sourcePackage=null 的绑定仍可读、可发布、可交付。只改名称/分类/排序时不要求补传 ZIP；替换素材走新接口。无需迁移所有已上传作品，不改已交付包的哈希/签名。已发布或被引用源包内容不可覆盖，上传修改后的 ZIP 生成新身份。
