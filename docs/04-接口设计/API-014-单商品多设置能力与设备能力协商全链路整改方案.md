# API-014 单商品多设置能力与设备能力协商全链路整改方案

**版本：** 1.0.0

**日期：** 2026-09-17

**对应任务：** WP-UI13

**状态：** 已确认并实施 Java API、V9、OpenAPI 2.1.0 和管理后台；App 按 [API-015](API-015-设备能力目录与多形式交付App对接说明.md) 及 [API-017](API-017-设备目录精确能力筛选App交接确认说明.md) 联调

**废止原方案：** [API-013 非 4D 动态/静态双形式交付与管理后台对接说明](API-013-非4D动态静态双形式交付与管理后台对接说明.md)

本文是 App、Java API、MySQL、管理后台和 OpenAPI 的统一整改依据。各端不得再按“一个商品只能选择一种壁纸类型”或“动态作品必须自带静态版本”单独实施。

## 1. 产品结论

一款壁纸是一个商品，也是一次兑换和权益判断的最小单位。一个商品可以同时发布多种独立设置能力：

- Android 4D；
- Android 动态；
- iOS 动态；
- 鸿蒙原生动态；
- 通用静态。

管理后台决定商品发布了哪些能力，App 上报当前设备实际能够使用哪些能力，API 计算两者交集。只有交集不为空时，分类、精选、搜索、列表和详情才向该设备返回商品。

```text
商品已发布能力 ∩ 设备有效能力 ≠ 空集
```

同一商品在一台设备上只展示一次。若交集中只有一种能力，App 直接提供对应设置入口；若交集中有多种能力，App 让用户选择设置形式。

## 2. 必须统一的概念

| 概念 | 定义 | 不能混淆为 |
|---|---|---|
| 壁纸商品 `Wallpaper` | 标题、分类、封面、获取方式、排序和权益所属对象 | 单一资源格式 |
| 商品设置能力 | 商品已发布的精确 `deliveryPlatform + resourceType` 组合 | 商品类型标签 |
| 设备能力 | 当前手机实际能交给系统设置的资源组合和位置 | 品牌或系统名称 |
| 宿主系统 | 手机真实运行的 Android、经典鸿蒙、新鸿蒙原生或 iOS 系统 | 当前安装包格式 |
| 运行环境 | 原生、Android 兼容层或 Android 容器 | 宿主系统 |
| 设置位置 | 桌面 `HOME` 或锁屏 `LOCK` | 一份新的壁纸资源 |
| 展示封面 | 首页、列表和详情使用的图片 | 通用静态设置能力 |

App 内陀螺仪或视频预览只证明客户端能够渲染内容，不证明宿主系统允许设置该壁纸。

## 3. 商品设置能力模型

### 3.1 唯一允许的资源组合

| 后台名称 | `deliveryPlatform` | `resourceType` | 必要 binding | 可被哪些设备能力匹配 |
|---|---|---|---|---|
| Android 4D | `ANDROID` | `LAYER_PARALLAX` | 4D 源包解析后的背景、前景、配置和封面 | Android 原生及保留 Android 壁纸接口的经典鸿蒙 |
| Android 动态 | `ANDROID` | `VIDEO` | `VIDEO:0` | Android 原生及保留 Android 壁纸接口的经典鸿蒙 |
| iOS 动态 | `IOS` | `LIVE_PHOTO` | `LIVE_PHOTO_IMAGE:0`、`LIVE_PHOTO_VIDEO:0` | iOS |
| 鸿蒙原生动态 | `HARMONYOS` | `THEME_PACKAGE` | `THEME_PACKAGE:0` | 新鸿蒙原生系统 |
| 通用静态 | `UNIVERSAL` | `STATIC_IMAGE` | `STATIC_IMAGE:0` | 实际支持系统静态壁纸设置的设备 |

不增加“早期鸿蒙资源类型”。早期鸿蒙若保留 Android 系统壁纸接口，设备能力直接匹配 `ANDROID / LAYER_PARALLAX` 或 `ANDROID / VIDEO`；它不能匹配 `HARMONYOS / THEME_PACKAGE`。

### 3.2 独立组合规则

五项设置能力互相独立，允许以下情况：

- 只有 Android 4D；
- Android 4D + iOS 动态；
- Android 4D + iOS 动态 + 鸿蒙原生动态；
- Android 动态 + 通用静态；
- Android 4D + Android 动态 + 通用静态；
- 只有通用静态；
- 其他由上述五项形成的有效组合。

不得因为商品存在动态能力而自动创建通用静态能力；也不得因为商品有封面而认为它可以设置为静态壁纸。

### 3.3 封面规则

`wallpaper.cover_asset_id` 继续表示商品唯一展示封面，但封面不参与设备能力匹配。

- 商品有通用静态原图时，管理员可以复用同一个 asset 作为封面和 `STATIC_IMAGE:0`，不重复上传文件。
- 4D 商品可以复用源包内封面。
- iOS 动态可以复用 Live Photo 的静态照片作为封面。
- 只有视频且没有可复用图片时，必须单独上传展示封面。
- 复用 asset 只减少重复上传，不自动产生新的资源变体。

## 4. 设备能力模型

### 4.1 上报字段

App 在设备注册和会话建立后上报最新能力档案：

```json
{
  "hostOsFamily": "HARMONY_CLASSIC",
  "hostOsVersion": "4.0",
  "sdkInt": 31,
  "manufacturer": "HUAWEI",
  "model": "example-model",
  "executionMode": "ANDROID_COMPATIBLE",
  "probeVersion": 1,
  "probedAt": "2026-09-17T08:00:00Z",
  "featureFlags": [],
  "capabilities": [
    {
      "deliveryPlatform": "ANDROID",
      "resourceType": "LAYER_PARALLAX",
      "runtimeOsVersion": "31",
      "placements": ["HOME"],
      "evidence": "SYSTEM_PROBE"
    },
    {
      "deliveryPlatform": "ANDROID",
      "resourceType": "VIDEO",
      "runtimeOsVersion": "31",
      "placements": ["HOME"],
      "evidence": "SYSTEM_PROBE"
    },
    {
      "deliveryPlatform": "UNIVERSAL",
      "resourceType": "STATIC_IMAGE",
      "runtimeOsVersion": "31",
      "placements": ["HOME", "LOCK"],
      "evidence": "SYSTEM_PROBE"
    }
  ]
}
```

建议枚举：

```text
HostOsFamily        = ANDROID | EMUI | HARMONY_CLASSIC | HARMONY_NATIVE | IOS
ExecutionMode       = NATIVE | ANDROID_COMPATIBLE | ANDROID_CONTAINER
WallpaperPlacement  = HOME | LOCK
CapabilityEvidence  = SYSTEM_PROBE | SUCCESSFUL_SET
```

`manufacturer` 和 `model` 只用于兼容性排查和服务端已知问题规则，不作为单独放行条件。

### 4.2 典型设备档案

| 设备 | 宿主系统 | 运行环境 | 应上报的主要能力 |
|---|---|---|---|
| 普通 Android | `ANDROID` | `NATIVE` | 经检测可用的 Android 4D、Android 动态、通用静态 |
| 华为早期 Android / EMUI | `EMUI` | `NATIVE` | 经检测可用的 Android 4D、Android 动态、通用静态 |
| 早期鸿蒙 | `HARMONY_CLASSIC` | `ANDROID_COMPATIBLE` | Android 4D、Android 动态、通用静态；不得上报鸿蒙原生动态 |
| 新鸿蒙原生 App | `HARMONY_NATIVE` | `NATIVE` | 鸿蒙原生动态、通用静态 |
| 新鸿蒙中的 Android 容器 | `HARMONY_NATIVE` | `ANDROID_CONTAINER` | 不得因能运行 APK 而上报 Android 系统壁纸能力 |
| iPhone | `IOS` | `NATIVE` | iOS 动态、通用静态 |

### 4.3 桌面和锁屏

资源版本不因设置位置重复上传。`placements` 表达当前设备能把同一资源设置到哪里：

- 只有 `HOME`：商品可以展示，App 只显示“设为桌面”。
- 只有 `LOCK`：商品可以展示，App 只显示“设为锁屏”。
- 同时有 `HOME`、`LOCK`：App 可以提供两个位置；仅当系统真实支持时才提供“同时设置”。
- `placements` 为空：该资源能力无效，不得参与目录匹配。

如果设备实测没有任何系统壁纸设置能力，App 应上报空 `capabilities`；API 保存空的有效档案并返回空目录，不得要求客户端伪造能力。

早期鸿蒙能设置动态桌面但不能设置动态锁屏时，仍然可以看到并使用对应商品。

### 4.4 `DevicePlatform` 的新边界

现有 `DevicePlatform` 继续表示客户端构建和设备凭据来源，不再决定目录可见性：

- Android APK 使用 `ANDROID`，即使它运行在早期鸿蒙或 Android 容器中；
- 鸿蒙原生 App 使用 `HARMONYOS`；
- iOS App 使用 `IOS`。

同为 `ANDROID` 客户端，`hostOsFamily`、`executionMode` 和能力列表仍然可能完全不同。Java 不得再用 `DevicePrincipal.platform` 单独决定壁纸资源；目录和下载必须读取设备能力档案。

## 5. 能力检测与多重保障

### 5.1 App 检测职责

App 不能用预览是否流畅判断设置能力。Android 类客户端至少检查：

1. 系统是否公开壁纸服务能力；
2. 当前用户是否允许设置壁纸；
3. 系统是否存在并允许进入对应设置流程；
4. 4D 所需姿态传感器是否存在；
5. 宿主系统和运行环境是否属于原生或可信 Android 兼容层；
6. 桌面和锁屏分别支持哪些目标位置。

用户真实完成系统设置后，App 将对应能力证据升级为 `SUCCESSFUL_SET`。系统接口明确拒绝或出现不可恢复的设置错误时，App 删除对应能力并重新上报；用户主动取消不能记为“不支持”。

### 5.2 Java 二次校验

服务端有效能力按以下公式计算：

```text
App 上报能力
∩ 服务端宿主系统/版本/运行环境允许规则
∩ 资源 minimumOsVersion
∩ 资源 capabilityRequirements
```

系统版本只用于校验和排除已知不兼容环境，不能在 App 未上报能力时单独授予设置能力。Android 容器即使返回 Android 版本号，也不得因此获得 Android 4D 或动态能力。

### 5.3 重新检测条件

以下任一条件发生时，App 必须重新检测并上报：

- 宿主系统升级；
- App 升级；
- `probeVersion` 升级；
- 系统设置能力调用发生明确成功或失败；
- 服务端返回能力档案过期错误。

能力变化后必须清理目录缓存、详情缓存和待用下载描述。

## 6. API 整改

### 6.1 能力上报接口

新增：

```http
PUT /api/v1/device/me/capabilities
Authorization: Bearer <device-session>
```

请求体使用第 4.1 节结构。写入必须校验：

- `deliveryPlatform + resourceType` 只能使用第 3.1 节合法组合；
- `placements` 非空、去重且只能为 `HOME`、`LOCK`；
- 同一能力组合只能出现一次；
- `sdkInt`、版本字符串、厂商和机型长度受限；
- `probedAt` 不得明显晚于服务端时间；
- `probeVersion` 必须处于服务端仍接受的范围。

响应返回：

```json
{
  "version": 3,
  "profileHash": "sha256-hex",
  "effectiveCapabilities": [],
  "recheckRequired": false
}
```

`effectiveCapabilities` 是服务端规则过滤后的最终能力，App 后续只能按该集合展示和申请下载。

### 6.2 设备目录

App 的分类、列表、搜索、精选和详情请求必须携带设备会话。现有目录路径可以保留，但语义改为设备个性化目录；无有效设备能力档案时返回明确错误并要求 App 先上报能力。

所有目录入口必须复用同一个可见性谓词：

```text
存在一个已发布 resource_version
且 wallpaper_variant 的 deliveryPlatform + resourceType
命中设备 effectiveCapabilities
且该能力 placements 非空
且 minimumOsVersion / capabilityRequirements 满足
```

以下位置必须同时整改：

- 分类列表及 `wallpaperCount`；
- 首页和精选；
- 分类壁纸列表；
- 搜索；
- 壁纸详情；
- 已获得壁纸列表中“当前设备可设置形式”；
- 下载票据。

不能只在手机端隐藏服务端已经返回的无效商品，否则分页总数、分类数量、搜索结果和流量都会错误。

### 6.3 公开 DTO

移除用单一 `kind` 表示商品能力的做法。目录摘要和详情返回当前设备实际可用的能力：

```json
{
  "id": "1001",
  "title": "山谷晨光",
  "cover": {},
  "availableCapabilities": [
    {
      "deliveryPlatform": "ANDROID",
      "resourceType": "LAYER_PARALLAX",
      "placements": ["HOME"]
    },
    {
      "deliveryPlatform": "UNIVERSAL",
      "resourceType": "STATIC_IMAGE",
      "placements": ["HOME", "LOCK"]
    }
  ]
}
```

服务端只返回当前设备可用能力，不把其他平台资源错误交给 App 自行猜测。

### 6.4 下载票据

将当前“按支持类型列表选第一个”的请求改为一次精确选择一个资源组合：

```json
{
  "deliveryPlatform": "ANDROID",
  "resourceType": "LAYER_PARALLAX"
}
```

服务端必须重新检查：

1. 该组合仍在设备 `effectiveCapabilities` 中；
2. 商品存在该组合的已发布资源版本；
3. 安全包已经就绪；
4. 商品为免费或设备已经拥有商品权益；
5. 设备会话、签名、限流和票据规则仍然有效。

请求的资源不可用时返回错误，不得自动换成静态或另一种动态形式。设置位置不改变下载包，不需要进入下载票据；App 在本地调用系统设置时使用 `placements`。

### 6.5 错误码

新增或明确：

```text
DEVICE_CAPABILITY_PROFILE_REQUIRED
DEVICE_CAPABILITY_PROFILE_STALE
DEVICE_CAPABILITY_INVALID
WALLPAPER_NOT_AVAILABLE_FOR_DEVICE
RESOURCE_NOT_SUPPORTED_BY_DEVICE
WALLPAPER_PLACEMENT_NOT_SUPPORTED
```

直接访问当前设备不可用的商品详情时返回 `WALLPAPER_NOT_AVAILABLE_FOR_DEVICE`，HTTP 可使用 404，避免与目录可见性产生差异。

## 7. 数据库整改

### 7.1 迁移原则

新增 Flyway `V9`，不得修改已经提交的 V1 至 V8。项目尚未上线，不迁移或兼容旧测试作品；旧壁纸和分类测试数据按既定清理流程删除后重新创建。

### 7.2 设备能力档案

建议新增一对一表 `device_capability_profile`：

| 字段 | 用途 |
|---|---|
| `device_id` | 主键并关联 `anonymous_device` |
| `host_os_family` | 宿主系统族 |
| `host_os_version` | 宿主系统版本 |
| `sdk_int` | Android SDK，可空 |
| `manufacturer`、`model` | 兼容性排查 |
| `execution_mode` | 原生、兼容层或容器 |
| `probe_version` | App 检测算法版本 |
| `reported_capabilities` | App 原始能力 JSON |
| `effective_capabilities` | 服务端过滤后的能力 JSON |
| `profile_hash` | 缓存和变更检测 |
| `probed_at` | App 检测时间 |
| `last_verified_at` | 最近真实设置成功时间，可空 |
| `lock_version` | 乐观锁 |
| `created_at`、`updated_at` | 审计时间 |

MySQL 保存最新业务事实，Redis 只缓存按 `profile_hash` 计算的目录结果，不把 Redis 当能力来源。

### 7.3 移除互斥类型事实

`wallpaper.kind` 当前要求 `PARALLAX_4D / DYNAMIC / STATIC` 三选一，与单商品多能力冲突。V9 应移除对应 CHECK、索引和列；管理写入、公开 DTO、筛选参数和 Java 枚举同步删除。

`wallpaper_variant`、`resource_version`、`resource_binding` 和 `secure_resource_package` 已能表达多能力商品，继续保留。唯一约束 `(wallpaper_id, platform, resource_type)` 正好保证同一商品每种能力只有一个变体槽位。V9 增加 `wallpaper_variant.enabled`，使管理员可以停用某一能力而不删除其版本历史。

## 8. Java API 整改清单

### 8.1 管理内容

`AdminWallpaperService`：

- 删除按 `WallpaperKind` 限制变体的 `validateVariantForKind(...)`；
- 改为校验第 3.1 节精确组合；
- 发布时允许任意一个或多个完整能力；
- 发布事务必须在退休旧版本前完成全部校验；
- 不强制动态能力绑定通用静态；
- 校验封面 READY，但封面不进入能力判断；
- 同一能力每次只能有一个 `PUBLISHED` 版本。

### 8.2 设备和目录

- `DeviceIdentityService` 在设备会话中关联最新能力档案版本和 hash；
- 新增能力档案写入服务和服务端策略过滤器；
- `PublicCatalogService` 的分类、计数、列表、搜索和详情统一使用能力交集；
- `PublicWallpaperViewReader` 只组装当前设备有效的 `availableCapabilities`；
- `DownloadTicketService` 精确匹配一个 `deliveryPlatform + resourceType`，不得跨能力回退；
- `DevicePrincipal.platform` 只校验客户端身份边界，不再单独授权资源类型；
- 缓存键至少包含目录参数和 `profileHash`。

### 8.3 服务端兼容规则

1.0 使用版本化代码或配置维护已知规则，不在管理后台开放任意编辑。例如：

- `HARMONY_CLASSIC + ANDROID_COMPATIBLE` 可以保留 App 确认上报的 Android 能力；
- `HARMONY_NATIVE + ANDROID_CONTAINER` 拒绝 Android 系统壁纸能力；
- `HARMONY_CLASSIC` 不接受 `HARMONYOS / THEME_PACKAGE`；
- `HARMONY_NATIVE + NATIVE` 不接受 Android 4D 和 Android 动态，除非未来有正式宿主接口和新的产品确认。

## 9. 管理后台整改

### 9.1 编辑器

删除“选择壁纸类型”的三选一控件，改为五张可独立启停的设置能力卡片：

```text
□ Android 4D
□ Android 动态
□ iOS 动态
□ 鸿蒙原生动态
□ 通用静态
```

选中后展开对应资源上传区域。至少选择并完成一种能力才可发布。

### 9.2 封面

封面独立于设置能力：

- 可以从已有静态图片、4D 包封面或 Live Photo 图片中复用；
- 没有可复用图片时单独上传；
- 后台必须明确显示“展示封面不代表可设置为静态壁纸”。

### 9.3 发布摘要

保存或发布前显示能力结果，而不是显示一个作品类型：

```text
已发布能力
Android：4D、动态、静态
iOS：静态
鸿蒙原生：鸿蒙动态、静态
经典鸿蒙：复用 Android 4D/动态，具体以设备检测为准
```

后台列表使用能力标签，例如：

```text
[Android 4D] [iOS 动态] [鸿蒙动态]
```

### 9.4 编辑与发布

- 已有能力可以创建不可变的新资源版本；
- 新增另一平台能力不创建新的商品；
- 停用某项能力只退休该变体的已发布版本；
- 商品至少保留一项已发布能力，否则应整体下架；
- 草稿能力不要求与其他能力一起发布；
- 批量发布多项能力必须保持事务原子性。

## 10. App 整改

### 10.1 当前实现必须重做的部分

现有 App 仍以单一 `kind` 组织详情，并只处理“动态/静态”二选一。整改后：

- 商品模型移除单一 `kind` 依赖；
- 使用 API 返回的 `availableCapabilities`；
- 一个商品可以同时有 4D、动态和静态选项；
- 只展示当前设备能力交集，不展示其他平台能力；
- 设置位置使用能力中的 `placements`；
- 本地安装状态按 `wallpaperId + deliveryPlatform + resourceType + resourceVersionId` 区分；
- 能力档案变化时清理目录缓存并重新加载。

### 10.2 卡片与详情

同一商品只显示一张卡片。标签只描述当前设备可用能力：

| 当前设备能力交集 | 卡片/详情表现 |
|---|---|
| 只有 4D | 显示“4D”，主按钮“设置4D壁纸” |
| 只有平台动态 | 显示“动态”，主按钮“设置动态壁纸” |
| 只有静态 | 显示“静态”，主按钮“设置静态壁纸” |
| 多种能力 | 显示多个标签，点击后选择设置方式 |
| 无能力 | API 不返回；App 本地也不渲染 |

详情预览默认使用当前设备能力中表现力最高的形式：Android 为 4D、动态、静态；iOS 为动态、静态；鸿蒙原生为动态、静态。用户最终选择哪种形式，只下载对应资源。

### 10.3 设置位置

选择资源形式后再根据 `placements` 展示设置位置：

- `[HOME]`：直接“设为桌面”；
- `[LOCK]`：直接“设为锁屏”；
- `[HOME, LOCK]`：允许用户选择系统真实支持的位置；
- 空数组：视为协议错误，不允许继续。

### 10.4 本地兜底

API 已完成主过滤，App 仍必须在显示设置入口和请求下载前复核：

- 能力仍在本机最新检测结果中；
- 资源类型与选择一致；
- 设置位置仍受支持；
- 系统调用明确失败时更新能力档案并刷新目录。

## 11. 权益和获取方式

权益继续绑定 `deviceId + wallpaperId`，不绑定平台、资源类型或设置位置。

- `REDEEM` 商品首次获得时消耗一次额度；
- 同一设备之后切换 4D、动态或静态不重复兑换；
- `FREE` 商品的所有可用能力继续免费；
- 用户每次只选择并下载一种形式，不预下载其他平台或其他形式；
- 设备没有任何有效能力时不能先兑换再发现无法设置。

## 12. OpenAPI 整改

这是破坏性契约变化，建议升级到 `2.0.0`，而不是继续增加 1.x 小版本。

新增 Schema：

```text
HostOsFamily
ExecutionMode
WallpaperPlacement
CapabilityEvidence
DeviceDeliveryCapability
DeviceCapabilityReport
DeviceCapabilityProfile
AvailableWallpaperCapability
ExactDownloadSelection
```

移除或废止：

- `WallpaperKind`；
- `WallpaperWriteRequest.kind`；
- 公开和管理摘要中的单一 `kind`；
- 目录的 `kind` 筛选；
- 下载票据请求中的多项 `supportedResourceTypes` 选择语义。

保留：

- `DevicePlatform`，但只表达客户端构建和凭据来源；
- `DeliveryPlatform`；
- `ResourceType`；
- 作品级 `REDEEM / FREE`；
- 不可变资源版本、安全包、设备会话和票据边界。

## 15. 验收用例

1. 后台可为同一商品同时创建 Android 4D、iOS 动态和鸿蒙原生动态。
2. 只有 Android 4D 的商品不向无 Android 4D 能力的设备返回。
3. 早期鸿蒙上报 Android 4D 后能看到同一商品，但不能选择鸿蒙原生动态。
4. 新鸿蒙原生设备只有在商品存在鸿蒙动态或通用静态时才能看到商品。
5. Android 容器不能因能运行 APK 或返回 Android 版本号而获得 Android 壁纸能力。
6. 支持动态桌面但不支持动态锁屏的设备能看到商品，且只显示“设为桌面”。
7. 同一设备有多项能力时商品只出现一次，并能选择本机可用形式。
8. 展示封面存在但没有静态变体时，不能产生通用静态能力。
9. 分类数量、精选、搜索、列表、详情和已获得列表使用同一可见性规则。
10. 直接访问不适用商品返回 `WALLPAPER_NOT_AVAILABLE_FOR_DEVICE`。
11. 下载票据只返回精确请求的能力，不回退到其他资源。
12. 同一商品先设置动态再设置静态不重复兑换。
13. 免费商品不需要权益，但仍执行设备能力、资源状态、安全包和限流校验。
14. 能力档案变化后旧目录缓存失效，重新请求得到正确内容。
15. 多能力发布任一项校验失败时，不退休当前任何已发布版本。
16. App 预览成功但系统设置能力缺失时，不把预览结果当作有效能力。

## 16. 本轮边界

- 不为早期鸿蒙复制一份新资源；它复用经过验证的 Android 资源能力。
- 不按品牌名称直接放行能力。
- 不允许系统版本号单独授予能力。
- 不让展示封面自动成为静态壁纸。
- 不为每个资源形式重复创建权益或消耗兑换额度。
- 不在管理后台开放未经验证的系统兼容规则编辑。
- 不修改已经提交的 V1 至 V8；数据库变化只通过新迁移完成。
- 本轮只完成代码、契约、迁移文件和本地验证；没有执行生产发布、生产迁移或生产数据操作。

## 17. 交付完成标准

WP-UI13 只有同时满足以下条件才能从“进行中”进入“待验收”或“已完成”：

1. OpenAPI 2.1.0、V9、Java API、管理后台和 App 使用同一能力枚举和匹配规则；
2. 原 API-013 的互斥类型和强制静态规则已从代码与文档清除；
3. 自动测试覆盖目录交集、平台资源组合、设置位置、票据精确匹配和权益复用；
4. 真实设备或经确认的设备能力样本完成跨端联调；
5. 项目管理看板、领域模型、数据库设计和验收记录同步更新；
6. 相关提交已推送，且没有密钥、运行时资源或测试数据库进入 Git。
