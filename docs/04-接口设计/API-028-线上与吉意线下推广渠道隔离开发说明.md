# API-028 线上与吉意线下推广渠道隔离开发说明

日期：2026-10-04。契约：OpenAPI `2.20.0`，数据库迁移：Flyway `V22`。代码分支：`codex/ios-acquisition-frontend`。

## 一、概述与确定范围

用户已确定：现有倾境动态壁纸三端继续作为正式 App；新增不上架商店的 Android 独立 APK“吉意壁纸”。管理后台可将某款商品设为“仅线下推广使用”，正式三端不展示、不提供其新的资源访问，吉意壁纸可以展示和兑换。

| 应用 | 安装标识 | 渠道 | 初始版本及更新 |
|---|---|---|---|
| 倾境动态壁纸 Android | `com.qingjing.bizhi` | ONLINE | 保持当前正式版本，独立递增 |
| 倾境动态壁纸 iOS | `com.qingjing.bizhi` | ONLINE | 保持当前 Bundle ID 与商店流程 |
| 倾境动态壁纸 HarmonyOS | `com.qingjing.bizhi` | ONLINE | 保持当前 Bundle Name 与商店流程 |
| 吉意壁纸 Android | `com.jiyi.wallpaper` | OFFLINE | `1.0.0` / `versionCode=1`，独立 APK 覆盖更新 |

吉意复用现有页面、图标、客服、免费领取及兑换码流程，使用同一 API 和业务数据库；本次不增加吉意 iOS/Harmony App，不增加登录、独立管理后台或新支付方式。这里的“线下”指推广分发渠道，App 仍需联网获取内容。

明确假设：吉意展示普通商品和仅线下商品；普通商品不是线上专属。两款 APK 可以同时安装，安装身份、本地缓存及下载记录分别保存，不迁移原 App 的设备身份。

这个开关表达分发范围，不表示已经获得素材授权。上传商品仍填写现有版权说明。

### 概念方案记录

核心用户为线下推广访问者；核心目标为区分正式三端与吉意的商品可见范围。三个功能：管理商品范围、服务端统一执行范围、吉意独立安装与更新。范围及名称已由用户确认，直接按下文实施。

## 三、字段与业务规则

### 1. 商品展示范围

新增 `WallpaperWriteRequest.offlinePromotionOnly: boolean`，响应 `AdminWallpaperSummary/Detail` 返回同名布尔值。

| 值 | 正式 Android、iOS、Harmony | 吉意 Android | 匿名封面/图标 |
|---|---|---|---|
| false | 按原平台资源能力展示 | 按 Android 资源能力展示 | 按原公开资源规则 |
| true | 不可见 | 可见 | 不可见 |

- 新建未传值：false。PATCH 未传值：保留现值；显式 false 可以关闭。
- 数据库字段：`wallpaper.offline_promotion_only BOOLEAN NOT NULL DEFAULT FALSE`。存量商品默认 false；不自动修改已有业务数据。
- 与 `accessType`、`previewWatermarkEnabled` 独立。免费/兑换、水印、资源类型和发布状态仍执行原规则，不复制或重新生成正式文件。
- 切换范围不删除购买/兑换事实、权益、资源或设备记录。正式 App 后续获取的列表、权益投影和资源请求重新检查范围，已保存在用户手机的文件无法追回。
- 未发布、资源未就绪、平台不支持的商品，吉意也不能绕过原校验。

状态机：普通展示 → 管理员保存 true → 仅线下展示 → 管理员保存 false → 恢复普通展示。乐观锁冲突返回 409，界面要求刷新后重试；保存失败不显示已生效。

### 2. API 渠道与资源访问

OFFLINE 唯一条件：MySQL 中当前 ACTIVE 设备的 `platform=ANDROID` 且 `app_install_scope=com.jiyi.wallpaper`。其他平台、包名及无会话请求均为 ONLINE。不增加 `channel=OFFLINE` 客户端切换参数。

分类、分类计数、推荐、搜索、列表总数及分页先执行渠道过滤，再计数/分页。详情、权益、兑换及其历史结果、免费领取、iOS 首免/商品/购买/恢复、预览票据、正式下载票据和各资源流入口均检查当前范围。

不允许只隐藏列表而让猜 ID、旧详情、旧预览链接或旧下载票据继续获取仅线下资源。已有短期票据每次读取时重新核对设备和商品范围；正式 App 请求仅线下商品时返回 404，避免通过错误消息暴露商品信息。其他发布状态或能力导致的兑换不可用继续沿用既有 `WALLPAPER_UNAVAILABLE` 结果。

封面及图标接口保持原路径：

| 接口 | 渠道处理 |
|---|---|
| `GET /public/categories` | 已认证设备；分类统计不泄漏隐藏商品 |
| `GET /public/wallpapers`、`/{wallpaperId}` | 已认证设备；服务端按登记范围过滤 |
| `GET /wallpapers/{wallpaperId}/cover?revision=...` | 普通封面可匿名；仅线下封面需要吉意有效设备 Bearer |
| `GET /public/assets/{assetId}/content` | 可选设备 Bearer；共享封面/分类图标也不能绕过仅线下范围 |
| 现有预览、兑换、下载及资源流接口 | 创建和消费阶段均执行当前范围 |

如果线上分类图标与仅线下商品复用同一原素材，线上分类使用该分类可见作品的按作品预览封面作为替代；原素材 URL 仍拒绝读取，不放宽原图公开条件。

吉意缩略图和分类图标使用设备会话请求头；只向 API 同源发送 Token，其他域名不附带。会话无效返回 401，不匿名回退；不可见返回 404；水印预览生成中仍使用原 503 状态，不回退原图。范围策略受服务器当前事实控制，公开资源使用禁止缓存的响应策略避免旧范围在代理中继续公开。

**认证边界：**当前 Android 安装凭据证明本机 RSA 私钥持有及登记 scope 绑定，不是硬件远程认证，也未验证实际 APK 的签名证书。正常正式客户端无法在既有会话中改字段切换渠道，但恶意客户端可以自行生成密钥、冒报已放行的吉意 scope 注册。因此这套机制是业务分发控制，不能称作不可伪造的保密隔离。不要把秘密访问资格建立在包名或 APK 内写死的密钥上；原有兑换、加密正式交付和水印规则继续保留。

### 3. 吉意 APK 与更新

- Gradle flavor：`offline`。包名与品牌集中在构建配置及 AppBranding，不修改 prod/iOS/Harmony 名称。
- 网络环境是 prod，API 为 `https://wallpaper.biguo66.top/api/v1`；不使用 local/internal 测试 API，不关闭 TLS、资源签名校验或版本门禁。
- 使用稳定正式 Release APK 签名和线上资源验签公钥。签名文件及密码只读私密配置，不进入 Git。
- 初始 `versionName=1.0.0`，`versionCode=1`；与倾境构建号完全独立。后续升级同时增加名称和构建号，真实元数据由系统读取，禁止靠文件名判断。
- 用户看见的是“吉意壁纸”；服务端登记安装 scope 与更新 check 中的 packageName 都由 Android 系统真实包名产生。

Android 版本管理新增应用选择“倾境动态壁纸 / 吉意壁纸（线下）”：

| 接口 | 新字段 |
|---|---|
| `GET /admin/app-releases?platform=android` | 可选 `packageName`，默认 `com.qingjing.bizhi` |
| `POST /admin/app-releases/android` multipart | 可选 `packageName`，默认倾境；必须与实际解析 APK 包名一致，否则 422 |
| `GET /app-updates/check` | 现有 `packageName` 接受吉意 Android；只返回其自己的版本和门槛 |

列表、发布递增判断、历史 APK 签名、最高可用版本、最低强制门槛均按所选应用分开。数据库既有 `version_identity` 对线上继续保存构建号字符串；吉意保存 `jiyi:<versionCode>`，允许两款 App 使用相同构建号，用户仍看到真实 versionCode。两款 APK 的上传/发布继续由平台锁串行，策略不互相影响。

App 更新业务拦截从已认证设备记录读取 scope，不能通过修改公开 check 的 packageName 绕过。下载完仍由客户端检查实际包名、版本、签名及 SHA-256，再调用系统安装器；错误 App 安装包不会用于覆盖更新。

更新状态沿用草稿 → 发布 → 弃用。未发布不提醒，弃用不参与判断；强制关闭后转普通更新。仅线下 APK 直接分发，不登记 Apple/Harmony 商店记录。

## 四、实施与交接顺序

1. API：V22、字段读写、共享渠道访问策略、资源入口过滤、Android 更新分包；同步 OpenAPI 2.20.0。
2. 管理后台：商品开关/范围列、Android 应用选择、上传包名验证提示；不直接操作数据库。
3. Android：offline flavor、品牌、同源会话封面及独立正式构建脚本。
4. 执行接口契约、API 单元与 MySQL 集成、后台测试/构建、Flutter 检查/测试，生成并核验吉意 Release APK；提交并推送。
5. **由用户部署 API 和管理后台**：使用本分支完成提交后的代码构建，遵循 [OPS-005](../07-部署与运维/OPS-005-环境与联调管理规范.md)，备份并运行 Flyway V22；API 配置 `QJ_DEVICE_OFFLINE_ANDROID_ENABLED=true`。这是新增登记放行开关，默认 false；原 Android provider 仍须启用。若部署环境显式设置 `QJ_API_CONTRACT_VERSION`，同步设为 `2.20.0`。所有正在接流量的 API 实例使用相同新版本与配置，不能新旧混跑后就开启商品开关。
6. 部署后通过后台开启测试商品的“仅线下推广使用”，安装吉意 APK验证。若要用于其后续更新，在版本管理中选择吉意，上传相应包并发布；单纯生成 APK 不会自动成为更新目标。

构建命令为 `scripts/package-offline-android.sh`。脚本只读本机正式配置，在当前代码工作树构建；不自动安装、不上传、不改数据库。默认输出在本机 Downloads 中的独立目录，包含 Release APK 和 SHA256SUMS；不放入 Git。可用 `--version-name` 和 `--version-code` 指定下一次独立版本。

本次不自动执行线上部署、线上数据修改或手机安装；用户要求后再按对应环境流程实施。关闭登记开关只阻止新的吉意注册，不撤销已登记设备；商品渠道范围仍以实时商品开关为准。

## 五、验收清单

| 场景 | 必须结果 |
|---|---|
| 存量普通作品 | 三端保持原可见性；吉意按 Android 能力可见 |
| 创建/编辑 true，省略及显式 false | 正确保留/切换，不由旧后台提交遗漏误清空 |
| 仅线下作品 | 正式三端分类/推荐/搜索/详情/权益不出现，吉意可以预览和兑换 |
| 正式设备猜 ID或重用旧票据 | 返回 404或既有不可用结果，不返回资源字节 |
| 匿名封面/共享图标 | 不泄漏仅线下资源；吉意有效会话可以请求对应封面 |
| 免费、付费水印及4D/视频 | 按原规则执行，不因切范围破坏原资源和水印 |
| 两款 App 同时安装 | 名称和包名正确，本地身份/数据分开 |
| 两款同构建号、不同版本策略 | 可以独立发布，各自查询只返回对应 APK；吉意强制不拦截倾境 |
| APK 上传选择与实际包不符 | 拒绝，不生成误归属版本记录 |
| 无数据/加载/保存失败 | 沿用现有空状态、加载和可重试错误文案，不把失败显示成成功 |

后续上架和素材授权决策独立于这个分发开关。
