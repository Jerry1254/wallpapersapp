## 1. 目标与已确认决策

为现有倾境壁纸平台补齐正式客户端，让用户在 Android、iOS、HarmonyOS 上浏览作品、获得权益，并使用所在系统实际支持的壁纸效果。

用户在本轮明确：

1. 三端必须一起首发，不能以 Android 单端上线作为本次完成标准。
2. iOS 接入苹果内购；Android 和 HarmonyOS 保留兑换码。
3. 延续现有产品和 H5 交互，不重新设计一套业务。

规划假设：面向中国大陆手机用户，不新增自建账号、跨 Android/iOS/鸿蒙权益迁移、订阅、广告或社交功能；发行渠道清单在 APP-00 记录。iOS 内购按可恢复的非消耗型商品设计，初期选择单作品买断；这是建议，不是用户已确定的定价或商品组合。

概念范围：沿用“首页 / 我的”双 Tab，围绕“浏览与预览、获得权益、下载与设置”三个流程建设。公共数据和服务端复用；支付、身份、资源处理和系统设置分别适配。

用户后续已接受平台能力差异：安卓完整建设动态锁屏、动态桌面和 4D；鸿蒙优先动态锁屏，桌面/视差逐项验证，不支持可不交付。具体实施按 PM-005，不要求三端桌面效果完全一致。

### 与历史基线的关系

原 PRD、ARC-001、PM-001、PM-003 中的“Android 首发、iOS/鸿蒙占位、本阶段无支付”属于此前阶段。新规划将三端正式交付及苹果支付纳入后续范围，不改变此前已验收的 H5/API 事实。

本轮保留 OpenAPI 1.0.1 和 9 文件冻结快照原字节。APP-01 才同步修订 PRD、ARC、SEC、DM、DB、API 和新快照；已执行 Flyway V1 不改写。以本文件作为后续范围变更说明，不能据旧门禁直接宣布三端可发布。

## 2. 三个平台的交付边界

| 功能 | Android | iOS | 原生 HarmonyOS |
|---|---|---|---|
| 首页、分类、搜索、详情、教程、客服 | 复用现有业务 | 同一内容体系 | 同一内容体系 |
| 获得权益 | 兑换码 | 苹果内购、恢复购买 | 兑换码，渠道审查列为前置门禁 |
| 我的壁纸、下载、更新、缓存 | 正式实现 | 正式实现 | 正式实现 |
| 静态壁纸 | 系统设置流程，按机型验证目标 | 保存至相册，用户在系统设置选择 | 验证公开设置接口；不满足时提供保存与设置教程 |
| 动态视频 | 原生 WallpaperService 播放 | 对可用素材制作 Live Photo；锁屏效果按系统规则 | 先验证普通应用权限及系统交付通道 |
| 4D 姿态视差 | 迁移已有 PoC，验证桌面渲染和生命周期 | App 内预览；不承诺第三方常驻桌面 4D | App 内预览与系统桌面能力分开验证 |
| 两分钟试用 | App 内预览，不设置系统壁纸 | App 内预览，不导出完整付费文件 | App 内预览，不授予正式权益 |
| 设置结果 | 系统可验证才记成功；取消和不可查询单独处理 | 只记“已保存”，不能推断“已设置” | 根据实际接口返回，不以打开系统页代替成功 |

Android 有公开的 [WallpaperService](https://developer.android.com/reference/android/service/wallpaper/WallpaperService)，现有 PoC 是可复用技术输入，不是所有品牌机型通过的证据。桌面、锁屏、两者及系统取消路径需要分别验证。

苹果官方说明 iOS 17 及以后可将 Live Photo 设置为锁屏壁纸，在唤醒时播放。[苹果设置说明](https://support.apple.com/en-ie/120734)。本产品以此作为 iOS 动态交付方向，不把它描述为循环动态桌面或 Android 式姿态壁纸服务；我们生成的配对资源仍须在目标真机验证。

华为手机按实际系统分组：能运行 APK 的旧系统进入 Android 兼容矩阵；原生 HarmonyOS 单独构建、签名和测试，不能把 APK 安装成功计为原生鸿蒙支持。本次未取得华为壁纸接口正文的可验证权限说明，因此不声称普通三方应用已经能设置视频/4D。主题中心内容能力不自动等于 App 可调用能力。

兼容性应在支付或兑换之前判断。没有可交付变体的作品不能出售或消耗额度；允许明确展示“不支持当前设备”，已有权益保留。详情显示“当前系统实际可用效果”，不能把封面或 App 内预览宣传成桌面结果。

## 3. 代码架构与复用策略

建议保留一个 Monorepo，即当前 wallpapersapp 仓库：一套 API、一套数据库、一套后台、一套资源业务模型。客户端共享程度由工具链验证决定。

优先方案：Android/iOS 使用上游 Flutter；HarmonyOS 使用经过验证的 Flutter-OH 适配工具链及 ArkTS 插件。Flutter 官方支持列表不包含 HarmonyOS，因此不能假定上游 SDK 加一个目录即可构建三端。[Flutter 平台列表](https://docs.flutter.dev/reference/supported-platforms)

维护方提供独立的 OpenHarmony SDK/Engine 适配，当前查到的入口为 [CPF-Flutter/flutter_flutter](https://gitcode.com/CPF-Flutter/flutter_flutter)。这证明存在适配路线，不证明本项目依赖、壁纸能力和商店发布全部兼容。SDK、Engine、Dart、DevEco、插件组合在 PoC 中锁定到不可变版本，不直接追踪开发分支。

APP-00 给鸿蒙 Flutter 路线最多 5 个开发工作日验证：签名 release 构建、真机启动、HTTPS、列表、图片、视频、传感器、安全存储、下载与平台调用。共同 Dart/Flutter 包要在两套工具链都能分析、测试和编译；不能仅验证空白页面。

若核心插件或稳定构建在时间盒内不能通过，采用 ArkTS/ArkUI 独立鸿蒙客户端，同仓库复用 API 契约、设计 Token、资源规范和验收用例，明确不复用 Dart 页面代码。此分支仅是技术兜底，不代表鸿蒙系统权限限制被解决；权限不可用仍按功能门禁处理。结论形成 ADR，随后再大规模写页面。

建议目录（本轮不创建）：

```text
apps/
  mobile/                       Flutter Android/iOS 入口与各自 lockfile
  mobile-harmony/               鸿蒙构建入口及独立工具链配置
  h5-prototype/                 已验收原型、联调与交互参考
  admin-web/                    统一管理后台
packages/
  mobile-domain/               Dart 模型、用例、状态和 Repository 接口
  mobile-api/                  生成 DTO、HTTP 映射与错误恢复
  mobile-ui/                   Flutter 页面和设计组件
  wallpaper-platform-interface/ 类型化平台边界
  wallpaper-android/           Kotlin：渲染、身份、安装、系统设置
  wallpaper-ios/               Swift：媒体导出、身份、StoreKit 桥接
  wallpaper-harmony/           ArkTS：媒体、身份、系统能力桥接
  design-tokens/               JSON 单一视觉源，生成 Dart/ArkTS
  wallpaper-format/            包格式、manifest 与兼容规则
services/api-server/           内容、身份、兑换、内购、权益、下载
contracts/openapi/             Java/H5/Flutter/ArkTS 的共同契约
wallpaper-tools/               各平台资源制作、校验、加密
poc/                          技术验证样例与证据
docs/                         需求、架构、执行看板、验收与发布记录
```

上述是对 ARC-001 目录建议的后续修订，不是已有目录。若采用 ArkTS 兜底，mobile-harmony 包含其页面/业务实现，取消无用的 Flutter 鸿蒙桥接包；不要维护两套鸿蒙正式实现。

平台接口至少分离 `DeviceIdentity`、`WallpaperCapabilities`、`Preview`、`PackageInstaller`、`WallpaperApply`、`PurchaseProvider`。三端能力枚举及返回值可共用定义，通道生成器是否支持鸿蒙须独立验证。页面不散落机型判断；环境/支付策略不能只靠客户端布尔值授权。

H5 的 Vue 页面不直接变成 Flutter 页面。复用的是流程、Token、字段语义、错误处理和验收场景；正式页面重新实现。资源包仅包含受支持的数据和媒体，不作为代码热更新通道。

## 4. 购买、兑换与权益

苹果审核规则对数字内容解锁和自制兑换机制有明确约束；本轮已选择内购，因此 iOS 不提供直播付费码兑换入口或导向站外购买的客服话术。[Apple 审核规则 3.1.1](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase)。Android/鸿蒙保留兑换业务，但发行渠道能否接受要在 APP-00 核对，不能据苹果方案反推其他商店允许。

### iOS 商品建议

- 首版用“单作品买断”的非消耗型商品，一项商品稳定映射一个作品，首发挑选有限数量的精品作品。后续可研究固定内容合集，不先加入额度钱包和订阅。
- 页面价格、货币和购买状态来自 StoreKit，后台不手写价格欺骗性覆盖。后台商品映射与 Apple 商品审核状态共同决定可售。
- 已购作品发布新资源版本沿用原购买权益；不能重新映射 productId 让用户丢失旧内容。
- 用户取消、待批准、成功待确认、恢复中、退款/撤销分别显示。扣款成功但接口超时时提示“正在确认购买”，允许恢复，不要求重复支付。
- 无自建账号不等于不能恢复购买。同一 Apple 购买账户恢复可恢复的购买，应支持在其合适设备重新取回；不承诺跨 Android/鸿蒙同步，也不把一份苹果购买永久锁死在首次安装密钥。

苹果公开文档描述非消耗型购买的恢复流程。[恢复购买说明](https://developer.apple.com/documentation/StoreKit/offering-completing-and-restoring-in-app-purchases)。客户端选 StoreKit 2；服务端验证签名交易并接收 V2 通知，以服务器校验结果授予内容，不信任单独的 transactionId 或客户端成功布尔值。[Apple 服务端验签方向](https://developer.apple.com/documentation/storekit/validating-receipts-with-the-app-store)、[V2 通知](https://developer.apple.com/documentation/AppStoreServerNotifications/receiving-app-store-server-notifications)

### 服务端新增设计

1. 增加商品映射、商店交易、权益来源和通知幂等记录。名称与表结构在 APP-01 定义，不在规划阶段直接建表。
2. 兑换权益来源为 REDEMPTION，苹果来源为 APPLE_IAP；不创建虚假兑换码来表示苹果购买，不扣现有兑换码额度。
3. 同一交易只处理一次。原购买记录可在经过验证的恢复流程中授权多个合法 iOS 安装，不能用“交易绑定单设备”的唯一约束阻断恢复。
4. 恢复流程需要当前 StoreKit 证据、设备会话及服务端校验，设计首次关联/多安装恢复/购买账户切换/撤销规则。签名有效不等于可以把任意上传交易绑定任意设备；APP-01 必须定义防交易拷贝重放与恢复之间的边界，并在 APP-05 验证。
5. 一份设备作品权益允许关联多个授权来源；退款只撤销对应来源，仍有其他有效来源时不删除整体权益。旧数据关联和新约束要显式迁移。
6. 校验交易所属应用、商品、环境及撤销状态。通知支持重复、乱序、丢失后对账；生产接口拒绝 Sandbox 凭证。
7. 对外保留“我的权益”语义；新增订单验证/恢复/通知契约。现有必填字段或含义若不能兼容，使用新 DTO/接口版本，不能悄悄把必填 sourceRedemption 改成空值。

Android/鸿蒙继续使用安装凭据与服务端会话；分别验证安全存储、重装、系统用户变化及恢复范围，不使用硬件编号或 H5 secret 作为正式身份。没有可靠证明时明确告知无法自动恢复，不能默认重装必然找回。

## 5. 资源交付与正式交互

一件作品下有平台变体：静态通用图、Android 分层包/视频、iOS 静态/Live Photo、鸿蒙经验证的资源格式。后台发布前检查“文件合法 + 目标端能使用 + 对应商业入口可用”，支持分平台可见性，不把未适配资源卖给错误系统。

正式交付需要补齐现有门禁中尚未实现的能力：平台正式身份、短时票据、私有读取、加密包、manifest 签名、哈希、密钥信封、原子安装、失败清理、版本更新及磁盘不足处理。

两分钟试用保持 App 内体验：独立预览衍生资源/试用会话，不创建设备权益，不下发可导出完整付费原图。倒计时按单调时钟的截止点计算，进入后台不延长，回到前台检查过期；结束清理临时资源。是否限制重复试用是新运营规则，首版不新增总次数限制，也不声称试用资源无法被提取。

本地状态与服务端事实分离：

```text
未获得 → 兑换/购买确认中 → 已获得（以服务端为准）
已获得 → 下载中 → 校验/安装中 → 可使用
可使用 → 打开系统流程 → 已确认设置 / 已取消 / 结果未知
iOS 可使用 → 导出中 → 已保存至相册 → 设置教程
```

下载失败保留可重试状态，更新失败保留旧可用版本；已应用资源不能被普通缓存清理误删。下载完成不等于已经设置。离线可以使用已安装资源；退款后的在线授权停止与已导出文件无法回收是不同事实，不承诺远程删除用户相册内容。

## 6. Git、版本与构建规则

### 分支策略

- `main` 保存通过当前阶段门禁的集成基线，禁止强推覆盖历史。
- 每个可验收工作包使用短期分支，例如 `codex/app-identity`、`codex/ios-purchase`；测试与文档完成后合回 main 并同步 GitHub。
- 不建立长期 `android`、`ios`、`harmony` 三条产品分支。平台差异由目录、插件和渠道构建配置表达，共享修复只维护一份。
- 临近提审才建立 `codex/release-mobile-1.0`，仅接受首发修复；修复必须回合 main。后续单端紧急修复也要回合主线。
- 提交按 `feat(mobile)`、`feat(ios)`、`feat(harmony)`、`feat(api)`、`fix(...)`、`docs`、`test` 分类。任务状态以 PM-002 为唯一来源，不在每个目录维护互相矛盾的状态表。
- 正式执行时启用 main 分支保护与 CI 门禁；这是未来配置任务，本轮没有修改远程权限。

### 五类版本分开

| 版本 | 示例 | 控制方式 |
|---|---|---|
| 用户可见 App 版本 | 三端首发 1.0.0 | 产品功能版本；后续可单端发 1.0.1 |
| 平台构建号 | Android 10001、iOS 101、鸿蒙 10001 | 每个平台各自递增，拒绝包也不复用；实际格式遵循提审工具 |
| 服务端版本 | api/v1.1.0 | 与 App 独立发版，先兼容部署再放行客户端 |
| API 契约版本 | 当前 1.0.1；兼容扩展建议 1.1.0 | 语义版本不等于 URL 版本；破坏性更改需新接口/主版本和迁移期 |
| 壁纸资源/格式版本 | 同变体 versionNo=2；formatVersion=1 | 资源更新和 App 发版分开，已发布资源不可覆盖 |

建议不可变标签 `android/v1.0.0+10001`、`ios/v1.0.0+101`、`harmony/v1.0.0+10001`。不同平台因审核修复可能来自不同 commit，不强求同一个 SHA；共同首发清单记录每个标签、SHA、构建号和兼容契约，不能只写一个含糊的 v1.0。

每个发布清单保存：源码 SHA、各工具链精确版本、锁文件摘要、API/格式支持范围、包哈希、非敏感签名指纹、素材版本、测试报告、审核状态和回退方法。示例编号只是规则演示，不是已经存在的版本或包。

### 工具链与环境

- 锁定 Flutter/Dart、Flutter-OH/Engine、JDK/Gradle、Xcode、DevEco/SDK、所有插件及生成器。提交应用 lockfile；两套 Flutter 入口分别解析依赖，共享包保持兼容约束。
- `local / internal / lab / prod` 使用不同服务地址、数据、凭据和平台应用标识；调试包与正式包可并存。Android 正式 applicationId 已固定为 `com.qingjing.bizhi`，4D Lab 为 `com.qingjing.bizhi.lab`，详见 [OPS-004](../07-部署与运维/OPS-004-Android双包打包与命名规范.md)；后续版本不得改名。
- 发布签名私钥、Apple API 私钥、描述文件中的秘密、密码和 Token 放入受控凭据系统；保护签名身份连续性与加密备份，避免换机器后无法更新已发布应用。
- 当前 `.gitignore` 还需在工程创建时补齐 iOS/鸿蒙产物和凭据范围，例如 `.ipa`、`.hap`、`.app`、`.p12`、`.p8`、`.mobileprovision`，并采用路径/类型精确排除，不误排源代码。
- 不提交运行时文件、用户数据、上传壁纸、依赖目录和安装包；签名包、符号表/混淆映射及报告保存到受控构建产物存储。用已验证的产物提审，不在发布动作中临时换依赖重建。

## 8. 测试与同步首发

共同验收场景：后台发布三平台变体 → 各端真实目录/搜索/详情 → 预览 → 兑换或购买 → 服务端权益 → 安全下载 → 平台使用 → 重启和升级后恢复。每端用真机测试，不以模拟器、H5 或另一个平台通过代替。

关键失败路径：无适配资源不扣额度、不收款；会话过期；兑换未知结果续查；支付成功接口超时；恢复购买；购买账户切换；退款重复/乱序通知；下载中断/过期票据/磁盘满/包篡改；相册拒绝；设置取消；程序结束、设备重启；清缓存不删除当前资源；数据库新旧结构迁移；旧客户端读取新服务端。

CI 按改动触发：共享 Dart/UI 改动检查所有采用 Flutter 的客户端；平台插件改动至少跑本端及共享接口；OpenAPI/权益/下载改动回归 API、H5、后台及三端契约消费者；资源格式改动跑全部解析器。发行候选执行三端完整构建与端到端测试，某端没环境必须标记未测，不能算绿色。

设备矩阵在 APP-00 固定：Android 包括已有 Redmi K40 及首发渠道主要厂商真实设备；iOS 至少覆盖最低支持系统与当前支持系统真机，动态方向以 iOS 17+ 为起点提案；鸿蒙使用原生系统真机，旧 APK 兼容华为设备另列。最低 Android/HarmonyOS 版本在实际 SDK 与渠道要求核对后冻结，不能复制旧资料数字。

“一起首发”定义为同一发布窗口完成三端可下载与业务可用。先分别提审并等待，全部满足要求后才申请生产发布确认；不能一端通过就提前公开销售。能手动发布的渠道使用手动控制，不支持的渠道先制定同窗分发方案。审核完成和商店缓存传播时间不同，不能承诺同一秒可见。

任何一端核心流程或审核不通过，整批首发保持等待。不得以审核版隐藏入口、审核后远程打开未审核支付能力绕过渠道规则。后续单端修复可独立发布，首发同步不要求终身捆绑发版。

服务端先做向后兼容的结构扩展，保留旧消费者窗口；客户端出问题优先暂停分发、关闭有缺陷能力或发修复版。已经安装的商店 App 通常不能依靠服务器强制降级；数据库迁移也不按 Git 回退自动逆转。不得回滚或覆盖订单、兑换和权益事实。
