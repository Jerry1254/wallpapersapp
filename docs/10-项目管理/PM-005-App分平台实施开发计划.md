## 1. 已确认目标

1. 保留三平台框架，按安卓、鸿蒙、苹果顺序逐个实现、逐个真机验证。
2. 安卓先做完整业务样板，包含静态壁纸、动态锁屏、动态桌面、4D 壁纸。已有 PoC 是技术输入，正式插件迁移与目标机型验收仍需完成。
3. 鸿蒙必须落实动态锁屏交付；动态桌面和视差单独验证。如果只能实现动态锁屏，用户已接受以该范围交付，不因此否定整个鸿蒙端。
4. 苹果按静态与 Live Photo 锁屏交付方向实现，包含苹果内购和恢复购买；安卓和鸿蒙保留兑换码。
5. 沿用 H5 已确认的视觉、首页/我的双 Tab、分类/搜索/详情、两分钟试用、兑换、下载、教程及客服流程。Vue 页面按 Flutter 重写，业务/API/Token 复用。
6. 三端依次完成内部验收，全部满足首发条件后统一发布；安卓先验收不代表提前对外首发。
7. 本轮仅完成规划文档，所有实施任务从“待开始”起步；下一项为 WP-A00。

本计划取代 PM-004 中“三端 PoC 全部通过后才开始安卓”的顺序和 APP-00 至 APP-08 粗粒度排期，保留其共享架构、支付边界、版本规则和统一首发原则。旧 PM-001 的 WP-W17 至 WP-W20 对应工作在本计划细化，后续不以旧编号重复开工。

## 3. 实施方式与工程边界

- 每次只推进一个主工作包：读取输入 → PM-002 标记进行中 → 实现 → 相关检查与真机验收 → 文档记录 → 更新状态 → Git 提交及同步。
- 自动检查通过但缺少必要真机或人工验收时标记待验收，记录缺少的具体证据，不跳到已完成。
- 本文件保存任务内容、依赖和验收标准；所有实时状态只维护在 PM-002，避免两份看板状态漂移。
- 服务端唯一正式工程为 `services/api-server`；后台只走管理 API。MySQL 保存权益/交易事实，Redis 不作为唯一事实存储。
- Flutter 页面只调用平台接口，Android 通过 Kotlin 插件适配；鸿蒙和苹果先保留接口及显式不支持结果，进入各自阶段后才实现真实能力。
- Android 阶段不要求安装鸿蒙/iOS 工具链才能开工；不把未编译的平台标为支持。共享层避免依赖 Android 类、文件路径和系统壁纸服务概念。
- 正式目录沿用 `apps/mobile`；共享业务与平台包按 PM-004 分层。鸿蒙是否需要独立构建入口或 ArkTS 客户端，在 WP-H00 作技术决策，不能建立长期平台代码分支来解决差异。
- 平台能力同时包含效果类型和设置位置：STATIC/VIDEO/PARALLAX 与 HOME/LOCK/BOTH 分开表达。兑换/购买前检查真实可交付变体；按钮不支持时不消耗额度、不误售。
- 能力不足允许明确说明或隐藏入口，不能用封面、App 内预览、打开系统页面冒充设置成功。

### 安卓验收脚本

1. 后台分别发布静态、视频、4D 样本及有效资源版本，确认封面和详情可查询。
2. 新安装正式客户端，以 Android Provider 建立设备会话。
3. 未获得时完成两分钟 App 内试用，确认不产生权益或正式导出。
4. 兑换一张作品，后台读取正确的额度、设备和权益；重复兑换不再次扣减。
5. 下载并校验资源，模拟中断再恢复；查看我的壁纸与本地安装状态。
6. 依次验证动态锁屏、动态桌面、4D 及静态设置；记录系统实际选项和结果证据，不预设所有机型支持独立设置。
7. 更新资源版本并验证失败回退旧文件；重新启动 App/手机后验证当前资源和权益。
8. 多设备并发、会话过期、未知兑换结果恢复、空间不足与缓存清理通过；所有异常均无虚假成功状态。

性能阈值在 A07/A08 开始时按目标机型、分辨率、帧率和测试时长写入验收方案，A10 按同一条件复测；本计划不凭空给出未经测量的功耗承诺。

## 8. 每个任务的统一完成标准

1. 任务对应的功能和失败路径实现完成，不能只交付正常路径。
2. 运行受影响的静态检查、构建与必要单元/集成测试。涉及原生显示、系统设置、签名购买必须取得对应真机证据；模拟器只作补充。

4. 新平台修改共享逻辑时，回归已经验收的平台。尚未开始的平台记为未实现，不要求其构建提前通过，也不宣称三端测试已通过。
